## Принятые архитектурные решения

### Часть 1 (Блоки A и F)
- Разделение Rust-ядра на workspace (`src-rust/sim_core` + `src-rust/sim_wasm`).
- Потоковая изоляция в Web Worker, обмен данными через `Transferable ArrayBuffer` (без `SharedArrayBuffer` ради Android WebView), сохранение через мост `Worker → Main Thread → StorageAdapter` (IndexedDB / Capacitor SQLite).
- План разработки разбит на 10 последовательных этапов с обязательным зелёным CI.

### Часть 2 (Блок B: Модель данных Rust)
1. **Типизированные индексы (Newtype Handles)** вместо строковых ключей и указателей: `PersonId(u32)`, `PlayerId(u32)`, `ClubId(u32)`, `StaffId(u32)`, `CompId(u32)`, `ContractId(u32)`, `StringId(u32)`, `NationId(u16)`. Невалидный/отсутствующий индекс кодируется `u32::MAX` (`NONE_ID`), что экономит память по сравнению с `Option<u32>` в плотных массивах там, где важна компактность.
2. **Разделение Hot / Warm / Cold данных игрока**:
   - **SoA (`PlayerWorldSoA`)** для ежедневного обновления 18 000+ игроков: возраст, CA/PA, усталость/форма, статус травмы, контрактный статус, флаги развития хранятся в отдельных выровненных массивах.
   - **Компактные структуры атрибутов (`Attributes`, `HiddenAttributes`)**: 33 видимых атрибута (`u8` в диапазоне `1..=20`, с возможностью хранения дробного прогресса тренировок в отдельном `i8`/`u8` аккумуляторе развития `[0..100]` или `u16` fixed-point при росте, чтобы избежать скачков и потерь точности) и 9 скрытых параметров (`u8`).
   - **Cold-таблицы (`Person`, `PlayerCareerHistory`, `RetiredPlayer`)**: биография, строковые интернированные имена (`StringPool`), история сезонов хранятся отдельно и не попадают в кэш-линии дневных циклов.
3. **Матчевый движок в SoA + плоские буферы**:
   - `MatchPlayersSoA` для 22 активных игроков на поле (отдельные массивы `pos_x`, `pos_y`, `vel_x`, `vel_y`, `facing`, `stamina`, `intent`, `effective_attrs`) — максимизирует кэш-локальность и автовекторизацию в циклах 4 Гц.
   - `BallState` (позиция X/Y/Z, скорость X/Y/Z, спин X/Y/Z в `f32`) для 60 Гц подшагов физики.
   - `TickBuffer` с фиксированной схемой раскладки (`#[repr(C)]` заголовок + плоские секции `f32`/`u16`/`u8`) для передачи в JS без промежуточных аллокаций и сериализации JSON.
4. **Отказ от `#[repr(packed)]`**: все структуры используют естественное выравнивание Rust / `#[repr(C)]` (для ABI/буферов) с ручной сортировкой полей от большего размера к меньшему, чтобы исключить невыровненный доступ на ARM64 (Android) и WASM32.

### Часть 3 (Блоки C и E: WASM API и Оценка производительности)
1. **Единый объект-фасад `SimEngineHandle` в `sim_wasm`**:
   - Вместо разрозненных глобальных функций используется один `#[wasm_bindgen]` хэндл внутри Web Worker, владеющий `WorldState`, опциональным активным `MatchState` и предвыделенными буферами ввода/вывода (`tick_out_buf`, `event_out_buf`, `io_scratch_buf`).
2. **Zero-copy чтение WASM linear memory + Transferable Ping-Pong в Main Thread**:
   - Rust возвращает `(ptr, byte_len)` на предвыделенный буфер в линейной памяти WASM; Worker создаёт временный `Uint8Array(wasmMemory.buffer, ptr, len)` (без аллокации на стороне Rust) и копирует ровно один раз в переиспользуемый `ArrayBuffer` из пула, после чего передаёт его в Main Thread с нулевым копированием через `postMessage(msg, [buf])`. Main Thread возвращает буфер обратно в пул после отрисовки.
   - JSON через границу WASM используется **только** для редких управляющих запросов/карточек и импорта баз данных, никогда — на горячем пути тиков матча.
3. **Предварительный теоретический бюджет памяти (18 000 игроков, ~600 клубов, ~40 турниров)**:
   - Все слои 18 000 игроков (`SoA` + `Warm` + `Attributes` + `Hidden` + `Person` + `Cold` + `Contracts`) ≈ **5.6–7.5 МБ** (включая горячий `PlayerWorldSoA` ~324 КБ).
   - Весь `WorldState` (игроки + клубы + персонал + `StringPool` + турниры + Fog of War + трансферы) ≈ **12–18 МБ** в начале карьеры, до **25–35 МБ** после 15 сезонов.
   - Активный матч (`MatchState` + `events` + scratchpad) ≈ **~64–128 КБ**; WASM-буферы обмена ≈ **~1–2 МБ** (из которых `TickBuffer` пакет = единицы КБ, буфер сохранения = переиспользуемый `Vec<u8>`).
   - Суммарный целевой бюджет WASM linear memory на Android WebView: **< 64 МБ** (с запасом под стек, код и временные структуры сохранения).
   - Сжатое сохранение (бинарный кодек + LZ4/Zstd): ориентировочно **2–5 МБ** на слот (с A/B shadow-копией до 10 МБ на диске).
   - *Примечание*: все цифры — предварительные расчётные оценки, подлежащие обязательному подтверждению профилированием на Этапах 3, 5 и 10.

### Часть 4 (Блок D: Математическая модель)
1. **CA / PA (шкала `1..=200`)**: `CA` вычисляется детерминированно как взвешенная сумма 33 атрибутов с позиционной матрицей весов `W[pos][33]` + поправка на двуногость (`weak_foot_bonus`), нормированная в `[1, 200]`. Потолок `PA` ограничивает рост через мягкий демпфер запаса потенциала `headroom = clamp((PA - CA) / 25, 0, 1)` и жёсткий инвариант `CA_new <= PA` (при перерасходе на тренировках включается перебалансировка).
2. **Нелинейное развитие и старение по позициям**: раздельные возрастные окна пика (Вратари `28–33`, ЦЗ `26–31`, ЦП `25–30`, Вингеры/Фулбеки `22–27`, Нападающие `24–29`) и раздельные кривые спада для физических vs ментальных атрибутов. Вклад тренировок и игровой практики масштабируется нелинейно (лог/сигмоида по минутам) с учётом качества тренеров, инфраструктуры и `professionalism`.
3. **Физиология (6 контуров) и Травмы**: раздельные уравнения для краткосрочной усталости в матче (`stamina_cur`), межматчевого восстановления (`fitness`), сезонной усталости (`season_fatigue`), игрового тонуса (`sharpness`), итоговой боеготовности и экспоненциального риска травм (`hazard rate`) с накоплением риска рецидива (`reinjury_risk_acc`). Выписка после травмы не восстанавливает `fitness` и `sharpness` автоматически.
4. **3D-физика мяча (60 Гц)**: полунеявный Эйлер (Semi-Implicit Euler) с гравитацией, квадратичным аэродинамическим сопротивлением, силой Магнуса (`ω × v`), ветром, коэффициентом отскока и трением газона с поправкой на погоду; точность удара/передачи моделируется нормальным угловым шумом `σ`, обратно пропорциональным профильному атрибуту, хладнокровию и остаточной выносливости.
5. **xG и Utility AI (4 Гц)**:
   - Логистическая модель `xG = sigmoid(z)` по 8 факторам (дистанция, угол створа, часть тела, тип предшествующего действия, давление защитников, позиция вратаря, блоки на линии, фаза/стандарт) с калибруемыми коэффициентами `β` и разделением вероятности создания момента (`chance creation`) и реализации (`finishing` vs `shot_stopping`).
   - Utility AI выбирает действие через `softmax(U_i / T)` с температурой `T`, зависящей от `decisions`, `composure` и усталости, что естественно порождает индивидуальные ошибки без заскриптованных сценариев.
6. **Экономика, трансферы и Fog of War**: рыночная стоимость — мультипликативная модель от `CA`, `PA`, возраста, лиги, срока контракта и позиции; скаутинг вычисляет ширину интервала погрешности атрибутов `±Δ` от срока наблюдения, `judging_ca/pa` и знания региона (`known_regions_mask`); переговоры — многоэтапный торг с динамической точкой отсечения (`reservation_price`) и терпением (`patience`).
